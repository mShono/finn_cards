# Как заполнять карточку

Схема - `cards/schema.json`. Это описание для человека и для промпта LLM
(фаза 3); сама схема не копируется сюда - меняется в одном месте.

## Разбор текста на кандидатов

Берём слова и конструкции **выше текущего уровня** (ориентир простой:
незнакомое или употреблённое неуверенно, оценивается по CEFR). На каждого
кандидата - одна `note`.

- **Лемма, а не словоформа.** Текст даёт `haen`, `note.lemma` -
  `hakea`. Если сомневаешься в лемме - прогони через `lemmatize()`, не
  угадывай.
- **Определи часть речи до всего остального.** `detect_pos()` по
  словоформе из текста. Без этого `generate_forms()` дальше либо упадёт,
  либо тихо вернёт пусто (прилагательному нужен тег `+A`, не `+N`).
- Если `detect_pos()` вернул больше одного варианта - слово омонимично
  (`kuusi` - "ель" и "шесть", оба существительные с разными леммами).
  Смотри на контекст исходного предложения, не бери первый элемент
  списка.
- **`kind: "pattern"`**, когда ошибка/конструкция не сводится к одной
  лемме - управление глагола, устойчивое сочетание. `lemma` тогда -
  сама конструкция (`"hakea + partitiivi"`), `pos` не заполняется.

## Формы - только через FST, никогда не сочиняются

Это правило проекта, не рекомендация. Алгоритм уже реализован
в `generate_forms(lemma, pos)`:

1. `uralicApi.generate(query, "fin", dictionary_forms=True)` - если
   непусто, берём как есть.
2. Иначе `uralicApi.generate(query, "fin")` - весь список кандидатов.
3. Один кандидат - берём его.
4. Несколько кандидатов - это `ambiguous`, а не готовый ответ.
   `generate_forms()` не выбирает за тебя: он честно репортит
   неоднозначность в `FormsResult.ambiguous`, потому что первый элемент
   списка часто архаичный или разговорный (например,
   `olla+Sg1 -> 'oon'` вместо `olen`).

**Не бери `ambiguous`-варианты в `principal_forms` руками.** До фазы 3
(там появляется LLM-выбор из списка) такие формы остаются пустыми,
`forms_verified: false`. Использовать их в упражнениях на склонение
нельзя - это явное правило схемы.

`forms_source` в note - одно значение на весь набор `principal_forms`:
- `fst` - все формы разрешились однозначно (шаги 1-3);
- `fst+llm` - хотя бы одна форма ушла в `ambiguous` и ждёт выбора;
- `llm` - FST не вернул вообще ничего хотя бы для одной формы (для
  глаголов это обычный случай).

## Puhekieli

Разговорная форма (`mä haen` вместо `minä haen`) идёт в `meta.puhekieli`
**в обход `validate_form()`**. Она вне литературной нормы по построению,
прогонять её через анализатор - гарантированный ложный негатив.

## Границы FST

`validate_form()` проверяет, что слово существует в языке. Она не
проверяет, что оно уместно в этом предложении: `Haen töissä` пройдёт
анализ и останется грамматически неверным (падеж не тот). Это отдельная
проблема, для неё нужен либо отдельный проход LLM, либо принятие риска -
не путать с задачей самого валидатора.

## Дедупликация

Ключ уникальности note - пара `(lemma, pos)`, полученная через
`lemmatize()`, а не сырая строка из текста. LLM в фазе 3 возвращает как
"лемму" иногда словоформу - лемматизировать нужно и её тоже.

## Strict-схема для LLM (фаза 3)

`strict_schema.convert_to_strict(schema, "note", exclude=...)` собирает
из `cards/schema.json` схему, совместимую с `strict: true` у OpenAI.
Обязательно исключай `id`, `principal_forms`, `forms_source`,
`forms_verified` - это поля, которые заполняет наш код по формам из FST,
а не LLM: формы вообще не берутся у LLM, это правило проекта. Без исключения
конвертер упадёт с понятной ошибкой - это осознанное поведение, а не баг:
`principal_forms` - словарь с произвольными ключами, strict-режим такое
не умеет представлять в принципе.
